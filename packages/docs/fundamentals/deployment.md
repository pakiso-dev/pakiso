# Deployment

Getting a Causal-backed app running in production means coordinating three
separate things that are easy to conflate: **your app's own generated
Prisma client**, **`causal init`'s schema application against the real
database**, and **the CLI's own internal Prisma client**. This page spells
out what each one is for and the order they need to happen in.

#### Two independent generated Prisma clients

| | Generated by | Generated where | Consumed by |
| --- | --- | --- | --- |
| **Your app's client** | You, running `prisma generate` against your own copy of the schema (see [example-api's `prisma/schema.prisma`](https://github.com/causal-dev/causal/blob/main/packages/example-api/prisma/schema.prisma)) | Your own project, e.g. `./generated/<dialect>` | Your application code, via `new PrismaStorageAdapter(prisma)` |
| **The CLI's internal client** | `causal init`, running `prisma generate` against `@causal/storage-prisma`'s own bundled schema | `node_modules/@causal/storage-prisma/generated/<dialect>` | Only `causal inspect` / `causal replay`, via `createStorageAdapterFromEnv()` |

These are independent: running `causal init` does **not** produce the
client your app imports, and generating your app's own client does **not**
make `causal inspect`/`causal replay` work. Both schemas describe the same
`CausalRun`/`CausalEvent` tables, so they're interchangeable at the
database level — they just need to be generated separately, in whichever
environments need them.

Because every `generated/` directory is git-ignored (Prisma's query engine
binary is platform-specific), **both clients must be freshly generated in
every environment that needs them** — your CI build, your production
container image, and wherever you run `causal inspect`/`causal replay` from
— rather than relying on an artifact built on a developer's laptop.

#### Recommended sequence for a multi-replica deployment

Causal's storage adapters support per-run execution leases
(`leaseOwner`/`acquireLease`) specifically so multiple application replicas
can safely share one workflow engine, so a real deployment should assume
more than one instance of your app running concurrently against the same
database:

1. **Build** (CI, or your Docker build stage): run `prisma generate`
   against your own schema copy so your app's client lands in `./generated/<dialect>`
   next to your built code. Do this on the same OS/architecture your
   containers will actually run on.
2. **Release, once per deploy** (a dedicated CI job or a one-off
   migration/init container or Job — *not* part of your app's own start
   command): run `causal init` against the real `CAUSAL_DATABASE_URL`. It
   is safe to re-run on every deploy — `prisma db push` converges the schema
   to match the file, and the PostgreSQL trigger install is idempotent
   (`DROP TRIGGER IF EXISTS` + `CREATE OR REPLACE FUNCTION`) — but it should
   still run from exactly one place per deploy, not from every booting
   replica, since N replicas calling `db push` concurrently is both
   wasteful and an unnecessary race against the same schema.
3. **Start N app replicas**: each just needs `CAUSAL_DATABASE_URL` and the
   client already generated in step 1. Replicas should *not* also call
   `causal init`/`db push` at boot.
4. **Ongoing debugging**: run `causal inspect` / `causal replay` (passing a
   run id as an argument) from any environment where `@causal/cli` is
   installed and `causal init` has already populated its internal client
   against that same `CAUSAL_DATABASE_URL` (a debug container, bastion
   host, or your own machine over a tunnel/VPN). `causal replay`
   additionally needs a `causal.config.mjs` exposing your real registered
   workflow handlers — see [`causal replay`](/cli/overview#causal-replay-runid).

`causal init` is deliberately the one and only place that writes to the
database schema — keep using its `prisma db push` for every dialect,
including production PostgreSQL/MySQL, rather than introducing a second,
separately-tracked `prisma migrate` history alongside it.

#### Simple/single-instance deployments

If you're running a single instance (e.g. local development, a small
single-process deployment), there's no concurrency concern — generate your
app's client and run `causal init` once as part of the same deploy/boot
sequence, in either order, before starting the app.

#### Checklist

- [ ] Your app's own `prisma/schema.prisma` copy exists in your project
      (not generated directly against `@causal/storage-prisma`'s schema).
- [ ] `prisma generate` for your app's client runs in every environment
      that runs your app (CI build / Docker build), not just locally.
- [ ] `causal init` runs exactly once per deploy against the real
      `CAUSAL_DATABASE_URL`, from a release step — not from each replica's
      boot sequence.
- [ ] `CAUSAL_DATABASE_URL` is available wherever you later run `causal
      inspect`/`causal replay` for debugging.
